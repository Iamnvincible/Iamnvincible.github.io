# 第三章，程序在机器层面的表示

我们知道，计算机运行的是机器代码。经过编码的 0、1 序列能够操作数据，管理内存，读写磁盘上的数据，甚至能够通过网络和其他设备通信。
编译器遵循编程语言、目标机器指令集和操作系统的标准，通过多个阶段将程序源代码转换成机器代码。
GCC 是一个 C 语言的编译器，它产生的是汇编代码 (assembly)。汇编代码是机器代码的可读文本表示。随后 GCC 调用汇编器 (assembler) 和链接器 (linker) 从汇编代码生成可以被机器执行的机器代码。本章开始学习机器代码和它的可读文本表示————汇编代码。

用高级语言编程时，我们不需要了解程序在机器层面的实现细节。而在计算机发展的早期，用汇编语言编程时，程序员必须非常了解每个汇编指令才能执行一次计算。高级语言非常成熟的今天，编写程序比那个时代的效率更高也更可靠。这要归功于编译器提供的类型检查功能。经过高度优化的编译器生成的代码可以和汇编程序员手工编写的程序同样高效。但是，高级语言编写的程序可以在不同机器上编译运行，而汇编程序与特定的机器类型深度绑定。

学习机器代码的几个原因：
1. 即使编译器能够生成汇编代码，能够理解它对认证的程序员来说是一项重要的技能。通过合适的参数，编译器能够生成汇编代码，阅读代码，可以理解编译器所做的优化和代码的低效之处。第五章中将能了解程序员为了能让程序高效运行所做的努力。
2. 有时候，高级语言提供的抽象让我们缺少理解程序运行所需的信息。第十二章中，为理解多线程程序，直到多线程运行过程中如何共享和私有数据至关重要。这些信息都能够在机器代码层面体现。另一方面，很多程序可能受到攻击，使恶意软件进入系统。这需要了解程序运行时的控制流信息。很多程序利用系统程序的弱点，通过覆盖数据来控制整个系统。理解这些漏洞产生的原因和应当策略需要了解程序在机器层面的结构。对程序员学习机器代码的要求已经从直接用汇编语言编写程序转变为阅读和理解编译器生成的代码。

本章，学习将学习一种汇编语言并观察 C 程序是如何编译成这种语言。阅读汇编代码所要掌握的技能与编写汇编代码截然不同。我们必须理解编译器将 C 语言结构转变为机器代码的机制。相对于用 C 语言编写的表达式，有优化能力的编译器能够重新安排执行顺序，去除冗余计算步骤，用高效的操作取代低效的操作，甚至可以将递归转换会迭代。理解源代码和所生成的汇编代码直接的关系具有挑战性。这是一种反向工程，尝试理解系统构建的过程时通过结果来反推。在我们的目标中，系统是机器产生的汇编程序，而不是人类设计的有形物件或无形逻辑。这简化了反向工程任务，因为生成的代码会遵循有规律的模式，并且我们可以多次实验，让编译器为不同程序生成代码。在本章中，将会给出很多例子和练习来展示不同层面的汇编语言和编译器。在本章中掌握这些细节是理解更深入、更基础内容的前提。那些只要理解基本原理但不管心细节的人是在自欺欺人。花时间来学习这些例子，并通过练习来强化对这些知识的理解非常重要。

本章通过目前使用最为普遍的 x86-64 架构的机器语言作为切入点，逐个讲解机器语言的要点。这门语言最早为 Intel 的 16 位处理器设计，后来扩展到 32 位，再扩展到 64 位。在这个过程中，随着半导体技术的进步，新功能也逐渐加入其中以满足市场需求。其中 Intel 扮演了重要的角色，但其对手 AMD 也做出量重要贡献。竞争的结果让我们看到了这个架构的机器语言有很多为了向后兼容以往功能加入了很多功能，但这些功能往往不会被现代编译器和操作系统所使用。本章关注 GCC 和 Linux 所使用的全部功能的子集，以简化说明。

首先从 C，汇编语言和机器语言之间的差异开始。而后，介绍 x86-64 的细节，即表示和操作数据，实现控制流。可以了解到 C 中的控制流，如 `if`，`while` 和 `switch` 语句是如何在机器层面实现的。随后了解如何实现函数，程序如何维护一个运行时栈来实现数据传递以及在不同函数之间跳转，以及局部变量的实现。接着，考虑数据结构的实现，如数组、结构体、联合。有了这些知识的铺垫，我们就可以理解内存越界和缓冲区溢出攻击。我们还会介绍一些 GDB 调试的技巧。最后介绍机器如何实现浮点数的计算。

业界以及完成了 32 位到 64 位的升级。 32 位机器最多只能使用 4 GB 的内存空间（RAM），随着内存价格的降低和计算和存储需求的增长，使用超过这个限制的内存也变得容易起来。 目前的 64 位机器最多可以使用 256 TB 的内存空间，并且可以方便地扩展到 16 EB。尽管目前还难以想象有一个拥有这么大内存的机器，但要记住，在 32 位机器普及的二十世纪七八十年代也无法想象 4GB 这样“巨大”的内存空间。

本章只会关注在现代操作系统上编译 C 或类似语言得到的机器层级的程序。
因此，不会介绍那些为了支持在早期处理器上运行的程序所使用的功能。在那个时期，很多程序都由手工编写，程序员必须在有限的 16 位地址空间上挣扎。

## 处理器的进化史

Intel 处理器的产品线口头上称为 *x86*，早已经过了长期发展。最早从 16 位芯片开始，和很多公司一样都受限于那时候集成电路技术，做了很多妥协。从那以后，受益于技术的进步也为了满足更高的性能要求和对更高级操作系统的支持，芯片产品逐步发展。
下面列出了一些 Intel 处理器型号和关键功能，特别是影响到机器层面编程的功能。我们使用晶体管的数量作为衡量实现一款处理器复杂度的指标。单位中的 K 代表一千，M 代表一百万，G 代表十亿。
- 8086（1978 年，29K 晶体管）最早的 16 位处理器之一。8088 只比它多一个 8 位外部总线，成为了 IBM 最早的个人电脑的处理器。IBM 和当时还很“微”的微软签订了开发 MS-DOS 操作系统的合同。最早的型号有 32768 字节的内存和两个软盘驱动器，但没有硬盘驱动器。架构上限制了机器最大使用 655360 字节的地址空间，地址只有 20 位，操作系统保留 393216 字节。1980 年，Intel 引入了 8087 浮点处理器（45K 晶体管）与 8086 和 8088 一同工作，执行所需的浮点计算任务，称为 *x87*。
- 80286（1982 年，134K 晶体管）。添加了更多寻址模式，组成了 IBM PC-AT 个人电脑，也是最早的 Windows 运行平台。
- i386（1985 年，275K 晶体管）。32 位架构，添加了线性内存模型（程序可以访问连续的地址空间），这也是 Linux 和现代 Windows 所使用的内存模型。也是第一款支持 Unix 的操作系统。
- i486（1989 年，1.2M 晶体管）。提升了性能，并前把浮点运算单元集成到了同一个芯片上，但没有怎么改变指令集。
- 奔腾（1993 年，3.1M 晶体管）。提升了性能，添加了少量指令集扩展。
- 奔腾 Pro（1995 年，5.5M 晶体管）。引入了 P6 微架构。添加了一类条件 MOV 指令到指令集中。
- 奔腾/MMX（1997 年，4.5M 晶体管）。添加了处理整数向量的指令到指令集。每次操作的数据可以是 1/2/4 字节，每个向量总计 64 位。
- 奔腾 2（1997 年，7M 晶体管）。引入了 SSE 指令，用于操作整数或浮点向量数据。每个数据可以是 1/2/4 字节，向量长 128 位。因为后来的型号引入了二级缓存，增加到 24M 晶体管。
- 奔腾 4 （2000 年，42 M 晶体管）。SSE 扩展为 SSE2，添加了包括了双精度浮点的数据类型，以及用于处理这些数据类型的 144 个新指令。有了这些指令扩展，编译器就可以使用 SSE 指令而不是前面提到的 x87 指令来处理涉及浮点的代码。
- 奔腾 4E（2004 年，125M 晶体管）。添加了超线程（hyperthreading），可以在单个处理器上同时运行两个程序的技术。还添加了 EM64T，64 位指令集，这是 Intel 实现的 IA32 指令集的 64 位扩展。这个指令集由 AMD 设计，我们现在称作 x86-64。
- 酷睿 2（2006 年，291M 晶体管）。Intel 第一款多核处理器，就是在单个芯片上集成了多个处理器，但不支持超线程。
- 酷睿 i7，Nehalem（2008 年，781M 晶体管）。同时使用超线程和多核技术，最初版本支持在每个核心上执行两个程序，每个芯片上最多四个核心。
- 酷睿 i7，Sandy Bridge（2011，1.17G 晶体管）。引入了 AVX，是 SSE 的扩展，一个向量最多 256 位。
- 酷睿 i7，Haswell（2013 年，1.4G 晶体管）。扩展 AVX 为 AVX 2，添加了更多指令和指令格式。

每一代处理器都被设计成向后兼容，即更新的处理器能够运行在前代处理器上编写的程序。后面将会看到，很多奇怪的指令都是因为这个设计而存在。Intel 的处理器产品线有多个名字: IA32（Intel Architecture 32-bit）。Intel64，是对 IA32 的 64 位扩展，现在也称作 x86-64。我们使用通用的口头叫法 x86，这个叫法延续到 i486。

在处理器的发展过程中，有几家公司生产了能够兼容 Intel 的处理器，也就是能够运行完全相同的机器代码。其中最主要的公司就是 AMD，在其发展早期，它常常落后与 Intel 的技术，这让 AMD 采取了低价策略，生产价格更低性能也稍逊的处理器。2002 后，AMD 变得更有竞争力，率先突破了 1GHz 的商用处理器时钟频率的限制，也先引入了 x86-64 这个对 IA32 的 64 位指令扩展。虽然文中主要在 Intel 处理器上演示程序，但内容同样适用于它的竞争对手。

使用 GCC 在 Linux 操作系统上编译程序的程序员并不用关系 x86 指令集的复杂性。早期的内存模型和 x87 浮点指令集所使用的特性已经过时，尽管还是能够它演变的痕迹，但很多神秘的特性不会再出现。


## 程序的编码

使用 GCC 在 Unix 平台上编译这两个 C 源代码文件 `p1.c` 和 `p2.c` 的命令：

```bash
gcc -Og -o p p1.c p2.c
```

GCC 是 Linux 上的默认编译器，也可以使用 `cc` 来调用。命令行选项 `-Og` 表示编译器采用一定程度的编译优化但能够生成原始 C 代码结构的机器代码。更高级的优化可能会让机器代码难以理解。这个等级的优化在学习过程中非常有用，后面也会经常用到。在一些练习中也用用到 `-O1` 或 `-O2` 等级的优化来获得更好的程序性能。

使用 `gcc` 命令会调用一系列程序来把源代码转变成可执行代码。
1. 预处理。预处理器（preprocessor）展开源代码中的 `#include` 指令指定的头文件，展开所有宏定义。
2. 编译。编译器（compiler）为每个 `.c` 文件生成汇编代码 `.s` 文件。
3. 汇编。汇编器（assembler）将汇编代码转换为目标代码 `.o` 文件。目标代码文件是机器代码的一种，包括了所有指令的二进制表示，但尚未确定全局变量的地址。
4. 链接。链接器（linker）合并所有目标文件和所使用到的函数库（例如 `printf`），生成最后的可执行文件，文件名通过命令行指令 `-o p` 指定。可执行文件是另一种形式的机器代码，它是处理器真正执行的机器代码。两种形式机器代码的区别将在第七章讲述。


### 机器代码
如第一章所述，计算机系统使用了多种形式的抽象将具体的实现细节隐藏在简化的模型之下。其中有两个模型对机器代码的编程非常重要。
1. 指令顺序执行。机器代码编写的程序的格式和行为有指令集架构（ISA, Instructio Set Architecture）定义。ISA 定义了处理器的状态、指令的格式、每个指令对状态的影响。包括 x86-64 的大多数指令集架构将程序的行为描述为顺序执行，一条指令执行完成后，下一条指令才能继续执行。处理器硬件会更加复杂，可以并行执行多条指令，但它保证整体行为与 ISA 定义的顺序执行模式相匹配。
2. 虚拟内存地址空间。程序使用的内存地址是虚拟的地址，给程序提供一种可以使用很多内存的假象。其具体实现由多种内存硬件和操作系统共同完成，这部分将在第九章讲述。

编译器的作用体现在整个编译过程上，将由 C 语言代码定义的相对抽象的执行模型转化为处理器能够执行的非常基础、具体的指令。

汇编代码是一种非常接近机器代码的语言，相比机器代码，汇编代码是可读的文本形式，而机器代码是完全的二进制数字。能够理解汇编代码并能将其和 C 代码关联起来是理解计算机执行程序的关键。

机器代码和 C 代码差异非常大，一些处理器状态对汇编语言可见，但对 C 语言不可见。
- 程序计数器（Program counter, PC, %rip），处理器将执行的下一条指令的内存地址。
- 整数寄存器，共有 16 个，每个能存储 64 位数值。寄存器能够存储整数，也能存储内存地址，对应 C 的指针。部分寄存器用于存储程序状态，一些用于存放临时变量，如参数、局部变量、返回值等。
- 条件代码寄存器，存放最近执行的整数或逻辑计算的状态值，用于实现控制流、数据流，例如 `if` 和 `while` 语句。
- 向量寄存器，能够存放一个或多个整数或浮点数。

C 语言会根据数据类型来对待在内存中分配的存储空间，而对机器语言来说，整个内存就是一块很大的字节数组。数组、结构体是连续的字节，即使是 scalar 数据类型，汇编语言也不会区分是有符号还是无符号，是指针还是整数。

程序的内存空间包含了程序的可执行机器代码、操作系统需要的信息、运行时栈（用于管理函数调用、返回）、堆内存（用于用户申请的内存空间，如 `malloc`）。程序使用虚拟内存地址空间，对于 x86-64 虚拟地址空间使用 64 位表示。目前的实现将高 16 位置为 0，实际可寻址空间为 2^48，即 256 TiB。一般程序只会使用 MB 至 GB 级别的内存空间。操作系统管理虚拟地址空间，并能将其翻译到物理地址。

单个机器指令只能完成非常基础的操作。例如，将两个数相加，将数据在寄存器和内存间转移，跳转指令到另一个分支。编译器必须将程序中的结构生成为一系列指令来完成程序中的逻辑，例如数值计算、循环、函数调用和返回。

### 代码示例

给出一个 C 代码文件 `mstore.c`，包含如下函数定义。

```c
long mult2(long, long);

void multstore(long x, long y, long *dest){
    long t = mult2(x, y);
    *dest = t;
}
```

为了获得 C 编译器生成的汇编语言文件，使用 `-S` 参数，使编译器在编译阶段完成后停止，不调用链接器。

```bash
gcc -Og -S mstore.c
```

这会得到 `mstore.s`，一个包含了文本汇编代码的文件。关键部分代码如下，具体内容视编译器不同会稍有差异。

```asm
mulstore:
	pushq	%rbx
	movq	%rdx, %rbx
	call	mult2
	movq	%rax, (%rbx)
	popq	%rbx
	ret
```

如果使用 `-c` 参数编译，将会执行编译、汇编两个步骤。

```bash
gcc -Og -c mstore.c
```

得到一个目标文件（object-code）`mstore.o`，目标文件为二进制，不能直接打开查看文本内容。文件占用约 1.3KB 空间，反汇编后（反汇编器 `objdump`）查看代码段，关键部分的指令内容如下

```bash
objdump -d mstore.o
```

```
   0:   53                      push   %rbx
   1:   48 89 d3                mov    %rdx,%rbx
   4:   e8 00 00 00 00          call   9 <mulstore+0x9>
   9:   48 89 03                mov    %rax,(%rbx)
   c:   5b                      pop    %rbx
   d:   c3                      ret
```

左侧第一列为指令地址，中间部分为机器代码，右侧是对机器代码反汇编后得到的汇编代码。其中机器代码共 14 字节:

```
 53 48 89 d3 e8 00 00 00 00 48 89 03 5b c3
```
机器执行这个程序时，就是在执行这些指令。机器从这些机器代码中只得到很少有关程序源代码的信息。反汇编器将汇编代码解码得到了 6 条指令，一行一条，每条指令的长度有所不同。
- x86-64 的一条指令长度在 1 至 15 字节之间。常用和参数较少的指令被编码后指令长度会更短。
- 每条指令的指令编码唯一，因此才能被确定地反汇编出来。例如一个字节的机器代码是 `53` 那么它唯一对应指令 `push %rbx`。
- 反汇编器解码的唯一依据就是机器代码的字节顺序，不需要知道源代码。
- 反汇编器的结果和编译器生成的汇编代码会稍有不同，例如，反汇编结果中 `mov` 指令对应的汇编指令为 `movq`，省略的后缀 `q`。后缀和参数的长度有关，省略不会有影响。

生成可执行的代码需要链接器将多个目标文件链接起来，其中必须有一个目标文件中存在 `main` 函数。将下面代码编译成可执行文件。

```c
#include <stdio.h>
void mulstore(long, long, long *);

int main() {
  long d;
  mulstore(2, 3, &d);
  printf("2 * 3 --> %ld\n", d);
  return 0;
}

long mult2(long a, long b) {
  long s = a * b;
  return s;
}
```

```bash
gcc -Og -o prog main.c mstore.c
```
编译得到的 `prog` 可执行文件占用空间大约是前面 `mstore.o` 文件的好几倍，因为其中不仅包含了上面程序源代码对应的机器代码，还包括启动、终止程序以及与操作系统交互的代码。

再次调用反汇编器，对这个可执行文件反汇编。

```bash
objdump -d prog
```

输出的结果会比较多，其中包括上面程序源代码对应的反汇编结果。
```
00000000000011ab <mulstore>:
    11ab:       53                      push   %rbx
    11ac:       48 89 d3                mov    %rdx,%rbx
    11af:       e8 ef ff ff ff          call   11a3 <mult2>
    11b4:       48 89 03                mov    %rax,(%rbx)
    11b7:       5b                      pop    %rbx
    11b8:       c3                      ret
```
内容和前面的反汇编结果相似，注意到第一列的指令地址以及由链接器转移到了另一段地址。另外，`call` 指令调用的函数地址也发生了变化。链接器的一个作用就是确定函数调用的实际目标地址。书中原文例子中还会有 `nop` 指令用于字节对齐。


### 汇编代码格式说明

GCC 生成的汇编代码包含了很多我们目前尚不关心的信息。例如前面生成的 `mstore.s` 汇编文件的全部内容如下。
```asm
	.file	"mstore.c"
	.text
	.globl	mulstore
	.type	mulstore, @function
mulstore:
.LFB0:
	.cfi_startproc
	pushq	%rbx
	.cfi_def_cfa_offset 16
	.cfi_offset 3, -16
	movq	%rdx, %rbx
	call	mult2@PLT
	movq	%rax, (%rbx)
	popq	%rbx
	.cfi_def_cfa_offset 8
	ret
	.cfi_endproc
.LFE0:
	.size	mulstore, .-mulstore
	.ident	"GCC: (GNU) 15.1.1 20250425"
	.section	.note.GNU-stack,"",@progbits
```
以点 `.` 开始的代码是汇编器给链接器的说明，阅读时可以忽略。另外，汇编代码中也没有包含与源代码的对应关系。为了更好理解这些代码，后面的例子中会给出代码行号和解释。在上面汇编代码中加入助记后如下。

```asm
void mulstore(long x, long y, long *dest)
x in %rdi, y in %rsi, dest in %rdx

1 mulstore:
2	pushq	%rbx            保存 %rbx
3	movq	%rdx, %rbx      复制 %rdx 到 %rbx
4	call	mult2           函数调用 mult2(x, y)
5	movq	%rax, (%rbx)    将返回值存入 *dest
6	popq	%rbx            复原 %rbx
7	ret                     函数返回
```

这里只展示我们关心的代码片段。右侧的说明可以很好与原 C 代码联系起来。

在 C 代码中也可以加入汇编代码。一些需要使用更底层机器功能的程序（例如 [FFMPEG](https://github.com/FFmpeg/FFmpeg/blob/master/libavutil/x86/x86inc.asm)）会在代码中加入汇编代码。一种调用方式是用汇编编写一个完整函数，在链接时与 C 函数连接起来。另一种是内联汇编，GCC 支持在 C 程序中直接编写汇编代码。由于汇编指令依赖于指令集，编写的程序不能跨平台。

需要注意的是，本书中用到的汇编代码格式是 AT&T 格式，这也是 GCC、OBJDUMP 等工具默认使用的格式。在一些来自微软或 Intel 的工具和文档中，汇编代码可能会以 Intel 格式给出。GCC 支持使用参数 `-masm=intel` 来生成 Intel 格式的汇编代码文件。Intel 和 AT&T 汇编格式有以下区别：
- Intel 格式省略了指令字长后缀，例如 `pushq`、`movq` 在 Intel 格式中会是 `push`、`mov`。
- Intel 格式中寄存器前的 `%` 被省略。
- Intel 格式对内存位置的描述有所不同。Intel 使用 `QWORD PTR [rbx]` 而不是 `(%rbx)` 来访问寄存器 `rbx` 内容指向的内存地址，即将寄存器中的值当作指针，访问内存某个地址中的值。
- Intel 格式和 AT&T 格式指令的操作数顺序相反。

## 数据的格式

Intel 使用“字”（word）来表示 16 位长度的数据（最早的处理器是 16 位），“双字”（double words）表示 32 位数据，“四字”表示 64 位数据。下表展示了 C 语言中的基础数据类型的长度。64 位机器上的指针和长整型都是 64 位长度，本章中大部分例子使用指针和长整型作为数据类型。x86-64 指令集包含了所有字长的指令。浮点数有单精度和双精度两种，曾经 x86 将两种精度的浮点数都用 80 位实现。在 C 中用 `long double` 指定这种实现，但不推荐使用，因为不可移植到其他平台。

|C 数据类型| Intel 数据类型|汇编指令后缀|字节数|
|-----------|--------------|------------|------|
|`char`|Byte| `b`| 1|
|`short`| Word |`w` |2|
|`int`| Double Word |`l` |4|
|`long`| Quad Word |`q` |8|
|`char *`| Quad Word |`q` |8|
|`float`| Single precision |`s` |4|
|`double`| Double precision |`l` |8|

大部分 GCC 生成的汇编指令都会有一个长度后缀，表示操作数的数据字节数。例如数据移动指令有四种变体：`moveb`，`movw`, `movl`, `movq`，其中 `l` 代表 long word，也就是 4 字节，因为 32 位相比 16 位更“长”。但双精度浮点数也使用 `l` 后缀，这倒不会产生混淆，因为浮点数使用专属的指令和寄存器，不与整数计算共用寄存器。

## 读取数据

x86-64 处理器有 16 个通用寄存器（General-purpose register），可以存储 64 位数据（整数或指针），下表列出这些寄存器的说明。

|64位名称|32位名称|16位名称|8位名称|用途|
|--------|--------|---------|------|----|
|%rax    |%eax      |%ax     |%al    |返回值|
|%rbx    |%ebx      |%bx     |%bl    |被调用方需保护寄存器|
|%rcx    |%ecx      |%cx     |%cl    |第 4 参数      |
|%rdx    |%edx      |%dx     |%dl    |第 3 参数      |
|%rsi    |%esi      |%si     |%sil   |第 2 参数      |
|%rdi    |%edi      |%di     |%dil   |第 1 参数      |
|%rbp    |%ebp      |%bp     |%bpl   |被调用方需保护寄存器      |
|%rsp    |%esp      |%sp     |%spl   |栈顶指针寄存器      |
|%r8     |%r8d      |%r8w    |%r8b   |第 5 参数      |
|%r9     |%r9d      |%r9w    |%r9b   |第 6 参数      |
|%r10    |%r10d     |%r10w   |%r10b  |调用方自行保护寄存器 |
|%r11    |%r11d     |%r11w   |%r11b  |调用方自行保护寄存器 |
|%r12    |%r12d     |%r12w   |%r12b  |调用方自行保护寄存器 |
|%r13    |%r13d     |%r13w   |%r13b  |调用方自行保护寄存器 |
|%r14    |%r14d     |%r14w   |%r14b  |调用方自行保护寄存器 |
|%r15    |%r15d     |%r15w   |%r15b  |调用方自行保护寄存器 |

寄存器的名称体现了不同的命名约定和历史沿革。早期的 8086 处理器只有 8 个 16 位寄存器，`%ax` 到 `%bp`。寄存器的名称反应了它的用途。32 位处理器时代，寄存器名称在前面增加了 `e`，表示扩展（extension），`%eax` 到 `%ebp`。x86-64 处理器时代，这 8 个寄存器前缀变为 `r`,`%rax` 到 `%rbp`，同时增加了额外 8 个寄存器，`%r8` 到 `%15`，并使用了不同的命名规则。

x86-64 处理器的寄存器可以存储 64 位数据，当要使用较少位数据时，需要将寄存器名修改位对应长度的寄存器名称。修改低位寄存器时有两个约定。

1. 修改 8 位、16 位寄存器值时，这些寄存器中存在高位的数据。
2. 修改 32 位寄存器值时，高 32 位同时置零。

在这些寄存器中，`%rsp` 寄存器较为特殊，它作为栈顶指针寄存器使用，指向运行时栈的栈顶地址。一些指令在使用时会读取、写入这个寄存器。其他寄存器的使用更加灵活，但仍需要遵循使用约定，例如如何管理栈、如何传递函数参数、如何使用返回值和存取临时变量。后面的章节会具体介绍这些规则。

### 操作数修饰符

大多数指令有一个或多个操作数（operands），指定要执行操作的数据源和存放结果的位置。x86-64 支持的操作数形式如下表所示，初看会有些复杂，经过后面章节的巩固会得心应手。数据源可以是常数，也可以是在寄存器或内存中的值。指令执行结果可以存在寄存器或内存中。具体可以分为三种类型。
1. 立即数（immediate），也就是常数。在 AT&T 格式中，立即数需要以 `$` 作为前缀，值可以十进制或十六进制表示，例如 `$-577`，`$0x1F`。
2. 寄存器（register）。使用存在寄存器中的值。根据数据长度，需要使用对应长度的寄存器名称。表中使用 $r_a$ 标识任意一个寄存器，使用标志 $R[r_a]$ 引用这个寄存器中存放的值。可以将所有寄存器的组合想象成一个数组，通过寄存器下标来取某个寄存器的值，$r_a$ 就是这个下标。
3. 引用内存地址。通过一个计算得到的内存地址来访问对应内存地址的数据。把内存当成一个大数组，通过标志 $M_b[Addr]$ 来访问指定地址的值。下标 $b$ 表示数据位数，一般省略这个下标。下表中有多种内存取址模式，可以非常灵活地访问内存。最后一项表示最为通用的取址形式，$Imm(r_b,r_i,s)$。可以分为 4 个部分：立即数 $Imm$，存放一个内存基础地址的寄存器 $r_b$，索引偏移值寄存器 $r_i$，放大因子 $s$。其中放大因子必须是 1，2，4 或 8 中的一个。基础地址和索引偏移值寄存器都需要是 64 位寄存器名称。通过计算得到最终的内存地址。这种访问访问常见于访问数组、结构体。其他形式的内存访问可以依此类推。

|操作数类型|操作数格式|计算方式|类型|
|----------|-----|-----|----|
|立即数| $\$Imm$| $Imm$|立即数|
|寄存器| $r_a$|$R[r_a]$|寄存器|
|内存|   $Imm$|$M[Imm]$|内存绝对地址|
|内存|   $(r_a)$|$M[R[r_a]]$|间接内存地址|
|内存|   $Imm(r_b)$|$M[Imm+R[r_b]]$|内存基址+偏移|
|内存|   $(r_b,r_i)$|$M[R[r_b]+R[r_i]]$|内存地址索引|
|内存|   $Imm(r_b,r_i)$|$M[Imm+R[r_b]+R[r_i]]$|内存地址索引|
|内存|   $(,r_i,s)$|$M[R[r_i]\cdot s]$|内存地址倍数索引|
|内存|   $Imm(,r_i,s)$|$M[Imm + R[r_i]\cdot s]$|内存地址倍数索引|
|内存|   $(r_b,r_i,s)$|$M[R[r_b]+R[r_i]\cdot s]$|内存地址倍数索引|
|内存|   $Imm(r_b,r_i,s)$|$M[Imm+R[r_b]+R[r_i]\cdot s]$|内存地址倍数索引|

### 数据移动指令
移动数据是使用十分频繁的一类指令。这里列出的数据移动指令在数据源、目的类型上有所不同，也有不同的使用约定。这里将一些不同的之类归类，同一类型的指令完成相似的操作，只在操作数长度上不同。下表是 MOV 类指令。
|指令|效果|说明|
|----|-----|----|
|MOV $S,D$| $D\larr S$|数据移动|
|`movb`||移动字节（byte）|
|`movw`||移动字（word）|
|`movl`||移动双字（double word）|
|`movq`||移动四字（quad word）|
|`movabsq` $I, R$|$R\larr I$|移动 64 位立即数|

MOV 类指令将数据从源移动到目标，不会经过任何转换。根据指令的后缀不同，移动的数据长度也不同。数据源可以是立即数、存在寄存器或内存中的数值。数据目标可以是寄存器或内存地址。但数据源和目的不能同时是内存，也就是说，将内存中的数据移动到另一个地址需要两条指令。一条指令从内存读取数据存到寄存器，另一条将寄存器的数值存到内存中。移动时，指令的后缀、寄存器名称和数值必须在长度上匹配。除了 `movl` 指令在移动 32 位数值时会将高 32 位置零外，其他移动指令都只会修改与长度匹配的数据长度。x86-64 中约定，为寄存器赋值 32 位数据时，需要将高 32 位置零。

下面给出一个代码示例，注意上面提到的规则和上一小结操作数格式。

```asm
1 movl $0x4050,%eax     #立即数到寄存器 4 字节
2 movw %bp,%sp          #寄存器到寄存器 2 字节
3 movb (%rdi,%rcx),%al  #内存到寄存器   1 字节
4 movb $-17, (%rsp)     #立即数到内存   1 字节
5 movq %rax,-12(%rbp)   #寄存器到内存   8 字节
```

`movq` 指令在移动立即数时，只支持 32 位补码数，移动时会经过符号扩展到 64 位。`movabsq` 可以移动任意 64 位立即数，但移动目标只能是寄存器。

下面的一类指令 MOVZ 会在数据移动时扩展数据长度，扩展方式为 0 扩展。数据源可以是寄存器或内存，目的只能是寄存器。指令最后两个字母表示扩展的方向。注意没有 `movzlq` 指令，可以用 `movl` 指令替代，这利用了 32 位指令会将高 32 位置零的性质。

|指令|效果|说明|
|----|-----|----|
|MOVZ $S,R$| $R\larr$ ZeroExtend(S)|数据移动时 0 扩展|
|`movzbw`||从 byte 到 word 0 扩展移动|
|`movzbl`||从 byte 到 double word 0 扩展移动|
|`movzwl`||从 word 到 double word 0 扩展移动|
|`movzbq`||从 byte 到 quad word 0 扩展移动|
|`movzwq`||从 word 到 quad word 0 扩展移动|

MOVS 类指令会在数据移动时执行符号扩展。其中 `cltq` 指令没有操作数，它专门应用于 `%eax` 寄存器。其效果与 `movslq %eax,%rax` 相同，但在编码上更为简单。
|指令|效果|说明|
|----|-----|----|
|MOVS $S,R$| $R\larr$ SignExtend(S)|数据移动时符号扩展|
|`movsbw`||从 byte 到 word 符号扩展移动|
|`movsbl`||从 byte 到 double word 符号扩展移动|
|`movswl`||从 word 到 double word 符号扩展移动|
|`movsbq`||从 byte 到 quad word 符号扩展移动|
|`movswq`||从 word 到 quad word 符号扩展移动|
|`movslq`||从 word 到 quad word 符号扩展移动|
|`cltq`|`%rax` $\larr$ SignExtend(`%eax`)|将 `%eax` 符号扩展为 `%rax`|
